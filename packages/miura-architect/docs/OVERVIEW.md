# Miura Architect - System Architecture

## Overview

Miura Architect is a next-generation developer tool for visualizing and debugging miura-js applications. It provides real-time visibility into component hierarchies, signal flows, data flow patterns, and binding configurations.

**Vision**: A "Visual Brain Map" of your miura.js framework—like Figma for app architecture first, and a runtime debugger later.

This tool helps you answer:
- What is this app made of?
- Which components own which state, props, signals, stores, contexts, and API calls?
- How do parent/child components and data dependencies connect?
- Where are the important architectural boundaries?

Runtime activity rich the architecture map, providing live insights into signal changes, click/event tracing, and render performance.

## Data Sources

Miura Architect should merge two classes of data:

1. **Runtime data**
   - Provided by `miura-debugger` and the bridge.
   - Includes mounted components, live signal values, context resolution, store dispatches, and render metrics.

2. **Static manifest data**
   - Generated by a future Miura Vite step.
   - Includes declared properties, state fields, local signals, API endpoints, routes, source files, and ownership metadata.

Runtime data alone cannot reliably discover every prop/state/API name, especially when fields are not currently rendered or endpoints are imported through client modules. The architecture graph should therefore support an optional `ApplicationManifest` and gracefully fall back to runtime-only data.

## Core Communication Flow

### 1. Event Streaming (Phase 1 - Push-Based)

**Current (Polling)**:
```
Bridge → Polls every 1000ms → getComponentGraph(), getAllSignals()
```

**Target (Push-Based Runtime Layer)**:
```
MiuraDebugger emits event (signal write, component render, etc.)
         ↓
Bridge subscribes to specific event types
         ↓
Bridge sends push event immediately to server
         ↓
Server relays to all connected UI clients
         ↓
UI updates runtime metadata on the architecture graph
```

**Event Types**:
- `component:discovered` - New component mounted
- `component:updated` - Component render/update cycle
- `signal:written` - Signal value changed
- `signal:read` - Component/computed reads signal
- `store:dispatched` - Store action executed
- `@consume:resolved` - Context provider found
- `binding:created` - Template binding registered
- `timeline:event` - Generic timeline event

### 2. Real-Time State Synchronization

**Initial Connect**: Bridge sends snapshot of app state
```json
{
  "type": "APP_STATE_SNAPSHOT",
  "payload": {
    "components": [
      {
        "id": "comp_123",
        "tag": "my-component",
        "parent": "comp_456",
        "properties": { /* current values */ },
        "signals": ["sig_001", "sig_002"],
        "bindings": 5
      }
    ],
    "signals": [
      {
        "id": "sig_001",
        "label": "count",
        "type": "writable",
        "value": 42,
        "subscribers": 3
      }
    ]
  }
}
```

**Incremental Updates**: Events push deltas only
```json
{
  "type": "signal:written",
  "payload": {
    "id": "sig_001",
    "label": "count",
    "oldValue": 42,
    "newValue": 43,
    "timestamp": 1713984375123
  }
}
```

### Data Flow

1. **Left Panel** (Navigation & Browser)
   - Search filters components/signals in real-time
   - Select component/signal → emits `node:selected` event
   - Shows metadata (property count, render time, subscriber count)

2. **Center Canvas** (Architecture Graph)
   - Receives `node:selected` from left panel
   - Graph builder merges runtime snapshot and optional application manifest
   - Layout algorithm positions nodes left-to-right by hierarchy and dependency depth
   - Canvas supports pan, zoom, fit-to-view, and manual node positioning
   - Click node → update right inspector

3. **Right Panel** (Inspector)
   - Receives `node:selected` from canvas
   - Shows properties, state, signals, bindings (if component)
   - Shows value, subscribers, dependencies (if signal)
   - Shows state tree + action history (if store)
   - Copy, filter controls

## State Management Strategy

**No External Store** — Keep consistent with miura-element architecture:

```typescript
// Main App Component
@component({ tag: 'miura-architect-main' })
class MiuraArchitectMain extends MiuraElement {
  @signal() appSnapshot = { components: [], signals: [], stores: [] };
  @signal() selectedNodeId = '';
  @signal() filterTerm = '';
  @signal() filterOptions = { hideInternal: true, collapseUnused: true };
  @signal() isConnected = false;
  @signal() recordingSession = null;
  @signal() recordedEvents = [];
  
  // Derived signals for filtered/computed views
  @computed() filteredComponents = () => {
    return filterComponents(this.appSnapshot.components, this.filterTerm, this.filterOptions);
  };
  
  @computed() graphData = () => {
    return buildArchitectureGraph(this.appSnapshot, this.applicationManifest, this.selectedNodeId);
  };
}
```

**Event Handlers**:
- WebSocket message → update `appSnapshot`
- User search → update `filterTerm` (triggers `filteredComponents` recompute)
- User click node → update `selectedNodeId` (triggers `graphData` recompute)
- Socket disconnect → update `isConnected` = false
- Record button → update `recordingSession`, start buffering events

## Key Design Decisions

| Decision | Rationale | Trade-off |
|----------|-----------|-----------|
| **Push-based events** | Real-time responsiveness | Requires debugger enhancement |
| **MuiNodeCanvas for spatial graph** | Built on miura-ui, minimal deps | Less flexible than D3, but consistent with framework |
| **Property-driven state** (@signal) | Consistency with miura-element | No Redux/Vuex patterns |
| **Standalone web app** | Fast iteration, flexible deployment | Not browser extension immediately |
| **Server-side sessions** | Persistent recording | Extra infrastructure |
| **Read-only UI only** | Safer MVP | State mutation in Phase 2+ |

## Performance Considerations

### For Large Apps (100+ components)

1. **Virtual Rendering**
   - MuiContentTree: Handles automatically
   - MuiNodeCanvas: Implement viewport culling (only render 50 nodes)

2. **Event Batching**
   - Don't update UI on every signal write (high-freq animations)
   - Debounce updates to 16ms (1 frame)

3. **Memory Management**
   - Keep only last 500 timeline events
   - Prune old signal history after 1 minute

4. **Network Optimization**
   - Send delta updates (only changed properties)
   - Compress JSON for large payloads

### Signal Sensitivity

High-frequency signals (animations, mouse movement) will flood devtools:

**Solution**:
- Add `@signal({ hidden: true })` metadata to framework signals
- Auto-hide "internal" signals (starting with `__`)
- Toggle-able filter in devtools UI
